# Change: 将系统衣柜接入统一穿搭推荐入口

## Why

当前穿搭推荐仍由 `multimodal-agent` 根据自由文本直接产出候选。它没有使用已经整理的
中国男性系统衣柜、风格公式、季节/场景标签和单品图片关联，因此无法保证：

- 用户已选择的风格一定被保留；
- 推荐的每个单品可以追溯到系统衣柜中的稳定 `wardrobeItemId`；
- 固定业务流程与对话 Agent 得到同一套推荐逻辑；
- LLM 不会在目录之外编造衣服、品牌或搭配；
- 用户的选择、收藏、替换与试穿能成为后续偏好的强信号。

已有 `RecommendationApplication` 已承担推荐的幂等、归属、候选持久化与 provider
替换边界。本变更在这个边界之内加入一条**系统衣柜推荐**能力，而不是另建一套 Agent
专属逻辑。

## What Changes

- 增加一个唯一公开的业务工具 `recommend-wardrobe`。对话 Agent 可以直接调用；固定
  onboarding / 方案流程在收齐资料后调用同一入口。低层检索、排序、文案生成均为私有实现。
- 将已经审阅的系统衣柜、风格公式、检索索引、图片与供给映射构建为服务端可部署的版本化
  只读目录快照；服务端不在运行时依赖 `client/` 相对路径。
- 在 `RecommendationApplication` 中实现确定性的「已选风格 → 公式 → 槽位单品候选」
  检索与软排序。身高、体重、体型、脸型、发量/发际线、场景、季节、正式度、维护成本及
  历史偏好影响排序，不把用户选定的风格硬拦截掉。
- 返回 1 套主穿搭、2 套备选公式；每个槽位返回系统衣柜单品与 3–5 个替换项。已选风格
  必须在结果中；可额外返回探索风格，但不能替代用户选择。
- LLM（若启用）只在确定性候选集合内撰写解释；其输出的单品 ID 必须是输入候选 ID，服务
  端拒绝未知 ID。第一版即使关闭 LLM 也必须能产出完整、可解释的结构化结果。
- 第一版不为系统目录或推荐 bundle 新增数据库表；目录 JSON 版本随结果返回，用户已有的
  方案/选择数据继续留在数据库。并为每个单品返回可展示资产状态：本地目录图只用于展示，
  只有已配置公开 URL 的服装单品才可进入真人试穿。
- 将推荐结果接入现有「选择风格 → 选择发型 → 穿搭 → 预览/方案落地」主流程，同时为
  Agent 对话调用保留同一审计、权限与幂等路径。

## Impact

- Affected specs: new capability `wardrobe-recommendation`; existing `style-recommendation`
  的穿搭实现将由自由生成过渡为目录约束的 hybrid / catalog-matching。
- Affected code: `RecommendationApplication`、Appearance Agent 工具装配、方案编排与
  读取接口、服务端目录构建脚本与测试；本变更不包含 Prisma schema/迁移。
- Affected data: 已有 `client/data/style-annotation/` 数据将作为内容源，构建后生成服务端
  部署快照；不把客户端开发目录作为运行时依赖。
- Out of scope: 商品实时价格/库存、自动下单、任意用户自建衣柜录入、以弱浏览行为训练偏好。
