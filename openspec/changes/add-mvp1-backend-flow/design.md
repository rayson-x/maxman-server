## Decisions

### 1. AI 编排：固定管道 + 对话 agent 双入口，共享同一套 step 实现
`产品决策`

首次进入走固定管道（可预测成本/延迟、可审计、安全规则由代码强制）；后续用户回来单独调整时走对话 agent，agent 通过 tool call 调用 **workflow 中的一部分能力**。两者共享同一份 step 实现，避免行为分叉。这要求每个 step 都是可独立调用、可独立重试的单元。

管道内部 5 个 step，对客户端只暴露两个可感知等待点：

| Step | 职责 | 队列 | 成本 | 耗时 |
|---|---|---|---|---|
| `S1 moderate-input` | 照片内容安全 + 用户自由文本双层审核 | `moderation` | 低 | <2s |
| `S2 analyze-vision` | 云端视觉分析（发型/胡须/眼镜/肤色/穿搭现状），合并客户端 `FaceMetrics` | `text-analysis` | ~¥0.001 | ~3s |
| `S3 recommend` | 风格向量硬过滤 → LLM 在兼容集内挑选 → 用户意向的对抗式评审 | `text-analysis` | ~¥0.01 | ~12s |
| `S4 render-previews` | 效果图生成 | `image-generation`（**并发必须=1**） | ¥0.2/张 | 13s/张 |
| `S5 materialize-plan` | 任务落位 + core/optional 判定 + 四阶段清单生成 | `text-analysis` | ~¥0.001 | ~3s |

### 2. 风格优先，而非发型/穿搭独立选择
`产品决策` + `逻辑推演`

发型和穿搭必须协调（"不能差距太大"），独立选择会产生不协调组合。但固定写死 4-6 个风格原型对用户没有吸引力（基本没有选择空间）。采用的方案是**用组合的机制做出固定风格的协调保证**：

```
用户数据（脸型/体型/年龄/身高体重/是否健身/场景/发际线/发量）
        ↓  确定性过滤：适配条件不符的条目直接排除
候选发型集合            候选穿搭集合
        ↓  确定性计算：风格向量距离 ≤ 阈值的组合才保留   ← 协调性在此保证，不经过 LLM
兼容组合集合（数量随数据量增长，全部保证协调）
        ↓  LLM：在兼容集合内挑选最适合该用户的候选 + 写推荐理由   ← 灵活性在此
候选方案 → 出图 → 用户选
```

**关键约束：LLM 的自由度在「从已保证兼容的集合里挑」，绝不在「判断什么和什么搭」。** 审美协调性是 LLM 最不可靠的判断类型，必须编码进数据。

风格向量四个维度（各 1-10）：

| 维度 | 含义 | 示例 |
|---|---|---|
| 正式度 | 商务 ↔ 休闲 | 背头+西装 = 9；寸头+连帽卫衣 = 2 |
| 成熟度 | 少年感 ↔ 沉稳 | 微碎盖+宽松T = 3；三七分+羊绒衫 = 8 |
| 张扬度 | 低调 ↔ 抓眼 | 黑色素T+直筒裤 = 2；漂染+印花衬衫 = 9 |
| 维护成本 | 每天几分钟 ↔ 需定期打理 | 寸头 = 1；纹理烫+每天吹造型 = 8 |

协调判定：各维度差值 ≤ 3（阈值可配置调优）。

选用向量而非兼容矩阵的理由：新增一个条目的标注成本是 **O(1)**（只打自己的分），矩阵是 **O(n)**（要和所有已有条目建立关系）。后者与"建立大量数据"的目标直接矛盾——数据越多标注量平方增长。

### 3. 两步约束选择：发型 → 穿搭
`逻辑推演`

同一个发型可以配多套穿搭（"不同穿搭相同发型"），所以发型与穿搭不是绑死的一对，而是一个兼容关系图。选择方式采用两步串行而非原子化组合：

1. **先选发型**（从适配集合，证件照底出 3 张预览）
2. **再选穿搭**（候选集由已选发型过滤，全身照底出 2-3 张预览）

四个理由：
- **可逆性不对称**（决定性理由）：发型剪了要等数周才能变，穿搭随时能换。不可逆的决策放第一步并给足对比，可逆的放第二步。
- 天然实现"不同穿搭相同发型"：发型定下后穿搭可反复换，不必重新决定发型。这也是「后续对话单独调用部分能力」的第一个真实用例。
- 图片生成压力分散到两次交互之间，用户思考时间天然掩盖并发=1 的串行延迟。
- 无全身照用户第一步完全不受影响，只在第二步降级。

推论：`guided_selection` 任务之间**可以串行依赖，但不能并列**（并列会导致候选组合爆炸）。

### 4. 目标图 = 基准照片 + 已完成账本 + 本阶段 core 计划变化
`逻辑推演`

前一份 spec 定义为「基准图 + 当前及之前所有 `ChangeManifestEntry`」，而 entry 只在任务 `status=done` 时写入。推导结果：阶段 N 刚解锁时账本里没有阶段 N 的条目，目标图与阶段 N-1 结束时完全相同——用户解锁新阶段看到的图没有变化，"目标"二字不成立。

修正后的口径：

- 目标图输入 = 基准照片 + 全部已完成 `ChangeManifestEntry` + **本阶段所有 `priority=core` 任务的 `change_description`（未完成但计划中）**
- **只有 core 任务进目标图，optional 不进**。core 集合同时定义「解锁条件」和「目标图内容」，两者一致；否则用户跳过/替换 optional 任务就要重算图
- 阶段内完成任务的过程中**不重新生成图**（图里已包含计划变化，完成任务只是"追上了图"），顺带省下大量生成成本
- `seed` 存于 `AppearancePlan`，全程复用，保证四阶段图像是同一个人的连续演变
- **阶段 0 不生成目标图**：全是仪容清理类变化，视觉差异极小，生成一张几乎看不出区别的图除了浪费 ¥0.2 还制造失望

`ChangeManifestEntry` 的角色由此明确：它是**已发生事实的账本**，不是生成图的唯一输入；生成图用的是「账本 + 本阶段计划」。

### 5. 几何判断归客户端，语义判断归云端
`实测`

云端 vision provider 对 `face_shape` 两家一致率 2/10，准确率约 20%。根因是把几何测量任务交给了语义模型。客户端 `client/lib/face/` 已实现并跑通：

- 完整几何：颞部宽/颧骨宽/下颌宽/下颌角宽/脸长/三庭/五眼比例 + 6 个派生比值，**全部以眼距归一化**（与拍照距离、分辨率无关）
- `faceShape` 分类带 `confidence` 与 `evidence`（支撑该分类的原始比值），支持向用户解释与人工校准阈值
- 质量检查：人脸数/居中/大小/光照/头部姿态（yaw/pitch/roll）+ 用户可读提示

分工：**几何测量与分类 → 客户端确定性规则；风格/美学/语义判断 → 云端视觉模型。**

脸型判定结果需**用户确认一次**（"量出你脸长/颧骨宽 = 1.32，属于长脸型，对吗？"）。成本极低，且带原始比值的说法比"AI 觉得你是长脸"可信得多。

### 6. 发际线/发量：组合判定 + 置信度分级
`实测`（客户端调研报告 17 例 + 云端 10 例）

单一信号不可用，组合后可用。决策矩阵：

| 信号组合 | 可靠性 | 可驱动的推荐调整 |
|---|---|---|
| `hairline ∈ {high, receding}` 且 `volume = thin` | ✅ 两个独立信号同时指向，短发者不会命中（短发不抬高发际线） | **强约束**：排除 `requires_hair_volume = high` 的发型（纹理烫、蓬松碎盖），优先短寸、textured crop |
| `hairline ∈ {high, receding}` 单独 | ✅ 误报率 0/17，唯一真后移者被判出 | **中约束**：排除 `covers_forehead = false` 的发型（大背头、飞机头、露额造型），优先碎盖、前刺、有刘海方向 |
| `volume = thin` 单独 | ❌ 短发者被误判（02-square 即为短发误判例） | **不约束**。正面照里"头发短"与"发量少"不可区分 |
| `hairline = occluded`（刘海遮挡） | — 本地不可测 | 降级到云端视觉语义判断（已验证 Qwen-VL / GLM-4V 能识别"后移"）或问卷自报 |

落地需要三件事：

1. **`StyleReferenceGuide` 增加两个约束字段**：`requires_hair_volume: low|medium|high`、`covers_forehead: boolean`。客户端上报的 `FaceMetrics` 以 `evidence_basis: visual_detected` 输入规则引擎做硬过滤——契合既有架构（LLM 只写文案，过滤/排序归规则引擎）
2. **问卷补一题脱发自报**：`AppearanceProfile.hair_loss_concern` 字段早已预留但问卷从未问。加"是否受脱发/发量变少困扰"→ `evidence_basis: self_reported`。与视觉信号交叉验证后，"发量明显不够"可达到驱动 core 任务的置信度（既有规则：`visual_detected` 或 `self_reported` 任一即可，两者都有则更稳）
3. **刘海遮挡用户的兜底**：`occluded` 占真实用户相当比例，交云端视觉模型语义判断

合规边界：发量/发际线必须表述为**造型可行性属性**（"这个发型需要的量感你不够"），绝不表述为**诊断结论**（"检测到你有脱发"）。与 `evidence_basis` 既有口径同线。

### 7. 阶段分配由数据决定，打分只管 core/optional
`逻辑推演`

前一份 spec 把「排序」和「阶段分配」当成一件事，实际依据完全不同：

| | 依据 | 例 |
|---|---|---|
| 阶段分配 | **时间尺度**（任务固有属性） | 剃胡须=10 分钟→阶段0；去理发店=预约+1 小时→阶段1；健身见效=6-12 周→阶段3 |
| core/optional + 顺序 | **优先级**（视觉收益/可信度/接受度/成本/风险） | 同在阶段1，"剪发"是 core，"换个手表"是 optional |

「健身减脂」打分再高也塞不进"当天 10-30 分钟"的阶段 0。修正后：

```
风格确定 → 发型 tag + 穿搭品类组合 → 展开成任务
非风格领域 → 从 CandidateTaskCatalog 取适用条目
  ↓  按各条目 applicable_stage_range 确定性落位到阶段 0/1/2/3
  ↓  每阶段内用加权公式算综合分 → 标 core/optional + 定 sort_order
四阶段任务清单
```

推论：**阶段 0 里几乎不会有风格相关任务**（发型要去理发店、穿搭要买/改衣服，都不是 10-30 分钟能完成的），阶段 0 基本是仪容清理类，这与决策 4 的"阶段 0 不生成目标图"互相印证。

### 8. 任务清单一次全生成，目标图懒生成
`逻辑推演`

前一份 spec 定的懒生成理由是省成本，但决策 7 之后这个理由反转：

| | 一次全生成 | 分阶段懒生成 |
|---|---|---|
| LLM 调用 | **1 次**（对整个候选集打分） | **4 次**（每阶段一次） |
| 成本 | ~¥0.001 | **约 4 倍** |

而**目标图必须懒生成**，理由比省钱强硬：目标图输入含「已完成账本」，而账本要等用户真的做完前面阶段才确定。提前生成阶段 2 的目标图，账本是空的，图就是错的——不是浪费，是逻辑上不可能。

适应性不丢：原本懒生成的另一个理由是"可参考实际完成情况调整"，这件事由 `progress_recheck` 显式承担，比藏在懒生成的副作用里更清晰可控。

### 9. 用户自由输入的双层审核
`产品决策`

采集形态为**混合**：核心硬字段走表单（快、零成本、100% 可靠，且固定管道需要确定的结构化输入才能跑打分公式）；「有没有中意的发型」走一个显式二选一 gate，选"有"才展开自由输入。

自由输入不能直接当 img2img 指令用（用户可能输入"把我变成女的"、"让我像某明星"、"把下巴削尖"，而产品有身份/骨架保留硬约束）。审核为两层：

1. **词库匹配**（确定性）：判断输入是否脱离发型/穿搭范畴
2. **LLM 审核**：判断是否越界

处理路径：先尝试归一化到目录 `style_tag` → 映射得上则用目录里**审核过的** `change_description` 生成；映射不上但通过审核的，走自由指令但**显式标注"这是你指定的方向，不在我们的推荐库内，效果仅供参考"**。

责任边界的划分方式与既有原则同构：正如 `evidence_basis=general_best_practice` 的任务永不可为 core、文案须用建议语气，**「你指定的方向」不能享有「我们推荐」的背书**。

红线（硬编码，不受模型判断影响）：改变骨骼/脸型/五官比例、改变性别/年龄/种族、变成某个具体真人、身体部位增强。

### 10. 用户意向分支：先生成他要的，再给我们的意见
`产品决策`

```
「有没有中意的发型？」
├─ 有意愿 → ① 先生成【用户中意的那个】在他脸上的效果图
│            ② 再给我们的意见（合适/不合适 + 理由）
│            ③ 连同我们的推荐一起摆出来
│            → 用户最终定（可能坚持自己的，也可能被说服换）
└─ 无意愿 → 直接给我们的推荐（不存在这个分支的开销）
```

**顺序是先生成再评判，不是先评判再决定给不给看。** 额外好处：让用户自己看到不合适，比用文字说服有效得多——他看着那张图觉得别扭，我们的"不推荐"理由才立得住。

这条路径 1:1 复用 `add-appearance-agent-foundation` 已建的三个工具，只把 `suggest-unconstrained-directions` 的输入源从"让模型自由发挥"换成"接收用户指定的想法"：

```
用户中意的  → 自由建议通道
我们推荐的  → 目录约束通道（向量过滤 + 打分）
                ↓
      adversarial-review-recommendations
      ├─ accept / reject / needs_professional_review
      ├─ reject 时必须给 reason        ← "不合适要给用户理由"
      └─ 两边一起返回                  ← "一起给用户看"
```

### 11. 身体数据是推荐引擎输入，不是图像生成输入
`实测`

实测证明：给 img2img 加入体型描述词后，模型会连脸一起重新生成（身份漂移比不加更严重）。因此：

- **作为推荐输入**（高价值、零风险）：身高/体重/BMI/体脂率/是否健身/肩宽/胸围/腰围/腿围 决定**推荐哪几套穿搭**。梨形身材避开紧身下装、肩窄的选有肩线结构的外套——这是穿搭领域真正的专业知识
- **不作为生成输入**：不让模型"造一个符合这些数字的身体"

无全身照时：只给文字穿搭方案（基于身体数据精准推荐）+ 通用示意图（明确标注非本人），并提示"上传全身照可以看到穿在你身上的效果"。**这是能力解锁而非强制门槛**——用价值引导上传，不拦路。`UserPhoto.photo_type` 本来就有 `full_body`，不是新增要求。

按此设计，若后续验证出可用的身份保留全身生成能力，只需把该分支的处理从"不给"换成"生成"，**流程骨架不动，不会返工**。

### 12. 并发=1 是硬吞吐天花板
`实测`

图片生成并发上限 1，每张 13-20 秒：

| 每用户图片数 | 全局占用 | 吞吐上限 | 10 人同时进来，最后一人等 |
|---|---|---|---|
| 6 张 | 78s | ~46 用户/小时 | 13 分钟 |
| 5 张 | 65s | ~55 用户/小时 | 10.8 分钟 |
| 3 张 | 39s | ~92 用户/小时 | 6.5 分钟 |

**并发池的粒度是 `req_key`，不是账号**（12.4 实测，修正了本决策早先的判断）：同时提交
`high_aes_general_v21_L`（文生图）与 `seededit_v3.0`（图生图），两者都拿到 task_id，
重叠约 9.6 秒无 `50430`。含义有限但明确——**同类工作无法靠换 req_key 加速**
（图生图池仍然是 1，上表不变），但文生图类的示意图可与本人效果图并行，不互相排队。

三项设计由此推导：

1. **渐进式推送**：S3 完成即返回文字推荐（~15s 用户已有内容可读），S4 每出一张推一张，**按匹配度从高到低提交**（并发=1 下完成顺序恒等于提交顺序，所以第一张必须是最推荐的）
2. **两步选择分散压力**（决策 3）：第一步 3 张，第二步 2-3 张，中间隔着用户的思考时间
3. **限流必须是「并发闸门」而不是「速率限制」**——这一条早先写错了，被 11.2 实测推翻：

   | 机制 | 实际语义 | 能否保证全局在飞 ≤1 |
   |---|---|---|
   | `rateLimiter.ts`（进程内） | 单 HTTP 请求最小间隔 600ms | ❌ 不约束在飞任务数，且仅进程内 |
   | BullMQ `concurrency: 1` | **每 Worker 实例**同时处理数 | ❌ 2 个实例 = 2 个在飞 |
   | BullMQ `limiter {max:1, duration:1200}` | **启动速率**：每 1.2s 最多放行 1 个 | ❌ 任务跑 19s，1.2s 后就放行下一个 |
   | `withVolcTaskSlot`（Redis `SET NX PX` 信号量） | 整个 `submit→poll` 生命周期持槽 | ✅ |

   实测现场：2 个 Worker + 6 个真实图生图任务，仅靠队列配置时最大在飞 = 2，**4 个被 `50430` 拒绝**。
   根因是速率限制 ≠ 并发限制。故实现落在 `lib/redisSemaphore.ts`，槽位按 req_key 分组
   （承接上文的池粒度结论），持槽覆盖全生命周期——因为供应商的并发计数看的是
   「服务端有几个任务在跑」，不是「有几个 HTTP 请求在途」。

   ⚠ 这个 bug 差点被漏掉：早前用假 processor（300ms）的队列测试是**通过**的，
   因为 300ms < 1200ms 限流间隔，任务从不重叠。快速替身掩盖了真实时序问题——
   涉及供应商并发约束的验证必须打真实调用。

   也不能退化成「只部署一个 worker」这种运维约定：一次副本数配错或蓝绿发布期间新旧并存，
   就会静默产生 429，而失败的是用户正在等的效果图。约束由代码保证，不由运维记性保证。

缓解手段优先级：减少每用户图片数（零成本，立即做）→ 接入第二个 provider 分流（阶跃星辰 Step-Image-Edit-2：0.5-2s、¥0.02/张，比火山快 10 倍便宜 10 倍，待验证）→ 花钱扩并发（规模上来后的兜底）。

### 13. 账本是自报的，`progress_recheck` 是校准器
`产品决策`

任务完成为纯自报（不设照片验证门槛）。风险很具体：用户点了"已剪成寸头"但实际没剪 → 阶段 2 目标图基于"他已是寸头"生成 → 用户照镜子发现图跟自己完全不像 → 直接击穿"看到自己"的核心承诺。

不采用强制照片验证，因为摩擦极大，且验证要靠刚被证明不可靠的视觉判断当裁判——误判"你没剪"比不检查更伤信任。

采用的方案：**不设门槛，设校准机制 + 声明责任边界**。

```
progress_recheck:
  ① 对进度照片跑视觉分析 + FaceMetrics
  ② 与账本声称的累计变化做一致性核对
  ③ 发现偏差 → 修正账本（对应 entry 标为未验证/回退）
  ④ 基于修正后的账本重新生成目标图
  ⑤ plan_version++
```

**偏差的表述必须是协作校准而非抓作弊**：「我们注意到方案里记录了"已剪成寸头"，但照片上看起来还是原来的发型，要帮你把进度改回未完成吗？」——这也顺带给了用户上传进度照的动力（它能让目标图变准）。

兜底：目标图旁标注"基于你勾选的完成情况生成"，零成本，责任边界清楚。

### 14. 换风格受已完成事实约束
`逻辑推演`

风格衍生任务（发型/穿搭）**不能单独替换**——单独换掉发型就破坏了整个决策 2/3 花力气保证的协调性。它只能表现为**换整个风格**。非风格任务（护肤/仪容/健身）可以从 `CandidateTaskCatalog` 同领域取等价条目替换，现有 `replaced` 状态够用。

换风格的语义：

- 已完成的 `ChangeManifestEntry` **全部保留**（事实不可撤销）
- 未完成的风格任务被新风格的任务替换
- **新风格候选集受已完成变化的向量兼容性约束**——复用决策 2 的同一套计算，零新增概念
- 目标图重新生成
- `plan_version++`（是同一方案的演进，不是新方案）

过滤到空集不是缺陷而是正确行为：用户已剪寸头却想换成需要中长发的风格，真相就是他得等头发长出来。正确文案不是"不行"，而是「**这个方向需要更长的头发，大约 X 周后可以考虑；现在能换的方向有这些**」——把物理约束转成时间预期。

### 15. 对话入口可写，限制手段是付费而非技术禁止
`产品决策`

对话允许调整目标/方案/目标图，走既有的 `user_regeneration` job_type（本就定义为"用户主动重新生成，消耗每周额度"）。`Subscription.weekly_image_quota` / `TargetImage.consumed_weekly_quota` 字段已在数据模型中。

MVP1 做法：**不设计费 gate，但正确记账**（`consumed_weekly_quota=true` 照写）。支付上线时开关一打开即生效，且这批数据正好用于校准定价（"用户平均每周想改几次"是定价的关键输入）。

**独立于计费的技术限流是必须的**（容量问题，非定价问题）：并发=1 的全局队列，一个用户在对话里连点 10 次"再生成"可占满队列 2 分钟以上，拖垮其他人的 onboarding。默认 **每用户每小时最多 3 次生成类操作**，即使支付上线后也保留。

对话 agent 与管道共享同一套 step 实现（决策 1），通过 DI 注入不同的工具子集实现权限差异——`createAppearanceAgent(deps)` 的 `tools` 字段本就是注入的。

### 16. 部分失败降级，目标图失败不阻塞阶段推进
`逻辑推演`

渐进式推送（决策 12）下"全或无"自相矛盾——已推送给用户的图无法收回。且重跑会重复烧钱。

- **自动重试 1 次**（与既有 `quality_checking` 的"重试一次然后失败"同口径，不新增规则），仍失败则降级为部分成功
- **部分成功必须可用且必须告知**：3 个候选出了 2 张，用户可在 2 张里选；但要明说「还有 1 个方案没能生成，要重试吗？」——静默少给一个选项会让用户以为我们只有 2 个方案
- **例外：阶段目标图只有 1 张，无"部分"可言。但它失败不该阻塞阶段推进**——目标图是激励物不是门槛（既有 spec 也规定生成失败不消耗额度）。阶段照常解锁、任务清单照常可见，仅在目标图位置显示"生成失败，点击重试"

| job_type | 覆盖 step | 相对归档提案 |
|---|---|---|
| `initial_analysis` | S1 → S4 | `full_analysis` 前半 |
| `outfit_preview_generation` | S4'（选定发型后） | **新增**（两步选择引入） |
| `plan_materialization` | S5 | `full_analysis` 后半 |

| `user_regeneration` | 对话/主动调整 | 保留，MVP1 记账不 gate |
| `progress_recheck` | 账本校准 + 重生目标图 | 升级为账本校准器 |

## Risks / Trade-offs

- **风格数据的生产是关键路径上的内容工作，不是代码能解决的**。最小可行规模估计：发型 20-30 条 + 穿搭品类 30-50 条，每条 4 个维度打分 + 适配条件 + 文案。用 LLM 生成初稿再人工校验是可行的，但要清楚这等于把 LLM 的审美判断从运行时搬到了数据生产时——只是变成了一次性、可人工复核的形态。
- **吞吐天花板 ~46-92 用户/小时** 意味着产品在接入第二个生成 provider 或扩并发之前不能做规模化推广。
- **风格向量四维度与阈值 ≤3 未经真实数据校准**，需要上线后用真实用户的选择行为回归调优。
- **`occluded` 发际线用户比例未知**，若比例很高则云端语义判断的调用量和不确定性都会上升。
- **账本自报失真在用户不上传进度照的情况下会长期存在**，目标图会持续偏离现实。缓解只有"标注责任边界"和"让校准变得有吸引力"。
