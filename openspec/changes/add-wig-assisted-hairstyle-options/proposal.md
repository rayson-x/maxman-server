# 变更：发型环节内的假发可选项

## 状态说明（必读）

**本提案是补立的：实现已经落在 `main` 上。** 按 `openspec/AGENTS.md` 的 Stage 1，新增能力与
schema 变更本应先立提案并过审批门，这一步当时漏了 —— 连续四轮 code review 都把它标为硬性
违规。本文把已完成的实现回填成规格 delta，并如实记录当时被推翻的方案，以便后来者知道
为什么最终形态是这样。

**不要把本文读成「待实施」。** 待实施部分只有 `tasks.md` 里标注为未完成的那些。

## 为什么

引导流的 `acceptance` 屏让用户自报「受脱发 / 发量变少的困扰」，最重一档是「明显困扰，
想重点改善」。但这个自报进系统后几乎不改变任何结果：它被映射成 `Hair Volume Signal` 的
`thin`，而仅「发量薄」按实测结论**不施加任何约束**（正面照分不清「头发短」与「发量少」，
据此过滤会误伤大量短发用户）。

真正的后果出现在发型推荐这一步：需要更多量感、或会把发际线暴露出来的款式被**静默剔除**。
这批用户看到的选项比别人少，而且不知道被剔掉的款式存在，更不知道存在另一条达成路径。
对「下周就要见重要的人」的用户，「养几个月发量再说」等于没有答案。

## 改什么

在发型推荐这一步多给一组选项，不改这一步的其它任何行为。

领域上先把一个混在一起的概念拆开（已写入根仓库 `CONTEXT.md`）：`Hair Volume Signal` 是对
用户**自身**头发的观察；`Available Volume Premise` 是他造型时**实际可动用**的发量。
**假发改变前提，不绕过约束。**

被剔除的那批款式不是黑箱：发型可行集来自确定性目录投影，被发量/发际线约束剔掉的部分是
**规则算出来的完整补集**，每项带明确原因。它们恰好是「只差发量或发际线」的款式。所以：

1. 目录投影照常给出用户当下就能剪的可行集（这一段不变）。
2. 被剔除的那批经一次**确定性查表**，判断每款需要哪种形态的假发（只补量感 / 整顶 /
   整顶且前额工艺过关），以及是否根本做不自然（极短露头皮款）。
3. 满足开放条件时，落成一个**独立的推荐集合**，用户可以真的选中其中一款。

**不新增任何模型调用。** 排序取自这一步已经在跑的模型通道。

## 影响

- 新增能力规格：`wig-assisted-hairstyle-options`
- schema：`RecommendationKind` 新增枚举值 `hairstyle_wig`（纯追加迁移）
- 发型属性表新增假发可行性维度（依据强度上限「逻辑推演」，无实拍对照）
- 发型可行集计算的排除项带出款式名与两项可行性属性
- 选定与方案落地接受该新集合类型；风格方向变更同样让它失效
- **不改**：风格方向选定、穿搭、出图链路、首轮分析、默认候选列表的产生与呈现
