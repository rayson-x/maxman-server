# Design: 双源多模态推荐流程

## Problem Statement

用户希望基于自己的年龄、身高、体重/体脂、围度、脸型、发际线、发量、当前外观、
日常场景、季节、预算和照片，先选定想要的风格，再得到真正适合自己的发型和系统衣柜方案。
当前两类知识源各有明显缺口：

- 自由多模态 LLM 覆盖面广、能提出目录外方向，但不可复现，可能忽略物理条件、现有资产或
  用户已选风格；
- 系统目录和规则可追溯、可落地，但数据尚不够成熟，若独占推荐会把未知案例误当作不适合，
  也会让产品只会推荐已经录入的有限风格。

两个 LLM 自由辩论不会产生真值，而且会增加延迟与成本。真正有价值的是让两个来源在相同
输入下产生可比较的结构化结果，由代码计算分歧，并记录用户实际看到和选择了什么。用户选择
是行为证据，不是客观正确性；只有结合曝光、位置和后续强行为事件，才能逐步判断系统知识
是否产生价值。

## Solution

建立一个内部共享的双源推荐引擎，并为风格、发型和穿搭提供三个独立领域工具。每个工具在
相同的多模态用户输入上并行运行：

- A 通道：只接收用户原始照片、结构化档案、场景及已选上游结果，不接收系统目录、规则或
  目录计数；
- B 通道：接收与 A 完全相同的用户输入，并额外接收全部适用的系统候选、规则及其稳定 ID、
  作用机制、证据等级和适用性判断。

两条通道使用相同 provider、模型、版本和生成参数，并输出同一领域 schema。服务端以版本化
确定性代码归一化、计算 diff 并组装结果：共识候选优先，随后是正确适用规则支持的 B-only
候选，最后最多一个没有硬冲突的 A-only 探索候选。用户只看到「推荐方向」和可选的
「探索方向」，不看到内部 A/B 技术标签。

产品路径固定为：

```text
双源风格推荐 → 用户选风格
→ 双源发型推荐 → 用户选发型
→ 双源系统衣柜推荐 → 用户选穿搭公式/单品
→ 预览与方案落地
```

每次运行写入结构化对照记录。高差异案例在结果返回后异步进入 reviewer；reviewer 只给内部
教研分类，不修改本次推荐。目录外探索条目用稳定概念 ID 保存；缺少资产时记录缺口并排队，
仍可先给用户展示和选择文字方案。

## User Stories

1. As a 用户, I want 风格推荐同时参考我的照片、身体数据和生活场景, so that 推荐不是泛泛的流行词列表。
2. As a 用户, I want 先选择自己明确喜欢的风格, so that 后续发型和穿搭不会把我的偏好替换掉。
3. As a 用户, I want 系统在我选定风格后再推荐发型, so that 发型与目标风格保持一致。
4. As a 用户, I want 系统在我选定发型后再推荐穿搭, so that 最终方案能解释发型与衣柜的协调关系。
5. As a 用户, I want 每个阶段都有少量清晰的主推荐, so that 我不必在几十个候选中自行做研究。
6. As a 用户, I want 在安全时看到一个目录外探索方向, so that 系统数据不完整时仍能发现新可能。
7. As a 用户, I want 探索方向与主推荐使用易懂标签, so that 我不需要理解内部 A/B 或算法术语。
8. As a 用户, I want 我的年龄、身高、体重、体脂、围度、脸型、发际线和发量都被纳入推荐, so that 推荐理由能对应我的真实条件。
9. As a 用户, I want 通勤、约会、日常、运动等场景影响推荐排序而不是一刀切拦截, so that 同一种风格能给出适配版。
10. As a 用户, I want 季节和真实天气参与穿搭判断, so that 推荐的衣服在我所在地可实际穿着。
11. As a 没有全身照的用户, I want 仍能根据录入的身体数据得到穿搭建议, so that 我不会因为缺少照片被阻断。
12. As a 没有全身照的用户, I want 系统明确说明未观察到我的身体比例, so that 推理不会伪装成视觉结论。
13. As a 用户, I want 系统只使用我的原始照片进行推荐分析, so that 生成图的偏差不会反过来污染推荐。
14. As a 用户, I want 目录外方案即使暂时没有图片也能先阅读和选择, so that 内容资产建设不会阻塞灵感推荐。
15. As a 用户, I want 缺少资产的方案明确显示图片尚未准备好, so that 我不会把占位内容误解为真实商品或本人效果。
16. As a 用户, I want 重复进入同一推荐阶段时看到同一批结果, so that 已经看中的选项不会无故消失。
17. As a 用户, I want 只有主动刷新或关键资料/上游选择改变时才产生新一代推荐, so that 结果变化是可解释的。
18. As a 用户, I want 某一 AI 通道故障时仍能拿到可用推荐, so that 临时模型故障不会让整个流程中断。
19. As a 用户, I want 系统数据不可用时明确说明结果是 AI 探索, so that 我不会误以为它通过了系统验证。
20. As a 用户, I want 删除账户或撤回人脸处理同意后清除可识别推荐档案引用, so that 对照研究不绕过隐私选择。
21. As a 推荐教研人员, I want 对同一输入下自由推荐与系统增强推荐进行结构化比较, so that 我能识别规则缺口而不是阅读长篇辩论。
22. As a 推荐教研人员, I want diff 按候选集合、排序、理由属性和硬冲突分类, so that 我能聚合查找最薄弱的规则。
23. As a 推荐教研人员, I want B 通道引用稳定 rule ID、作用机制、证据等级和适用条件, so that 我能判断规则是否被正确使用。
24. As a 推荐教研人员, I want 高差异案例自动进入异步复审队列, so that 人工精力集中在真正不确定的案例。
25. As a 推荐教研人员, I want reviewer 只输出结构化分类而不是自由辩论 transcript, so that 复审结果可检索、可统计。
26. As a 数据产品负责人, I want 记录用户实际曝光、位置与最终选择, so that A/B 采纳率不会因未曝光候选而失真。
27. As a 数据产品负责人, I want 保存、替换单品、明确不喜欢、保存试穿和最终采用等强事件, so that 后续优化基于行为强度而非浏览噪声。
28. As a 数据产品负责人, I want 用户选择被标记为行为证据而非审美真值, so that 团队不会用一次点击证明规则客观正确。
29. As a 目录运营人员, I want 目录外探索条目自动形成 CatalogGap, so that 我能知道下一批应补什么风格、发型或服装单品。
30. As a 目录运营人员, I want 被用户选择的缺失资产提高生成优先级, so that 资产生产围绕真实需求推进。
31. As a 目录运营人员, I want 后续把概念条目映射到正式目录条目而不改写历史推荐, so that 审计和采纳分析保持可复现。
32. As a 工程人员, I want 固定 workflow 和对话 Agent 调用同一领域工具, so that 两个入口不会产生不同推荐语义。
33. As a 工程人员, I want A/B 通道逐个幂等和独立重试, so that 一个通道失败时不会重复支付另一个成功通道。
34. As a 工程人员, I want 系统候选超出上下文时完整分批并确定性合并, so that 扩充目录不会造成静默丢数据。
35. As a 工程人员, I want 记录每个通道的模型版本、prompt 版本、成本、延迟和复用状态, so that 线上质量与费用可以追踪。
36. As a 隐私与合规人员, I want 日志只保存版本化引用和脱敏结构化结果, so that 不会在普通日志中复制照片、签名 URL、原始 prompt 或模型 transcript。
37. As a 产品负责人, I want 未来能按类似年龄、身高、体型和场景分析倾向, so that 数据成熟后可以引入群组匹配。
38. As a 产品负责人, I want 当前版本只收集群组分析所需字段而不提前上线群组算法, so that MVP 保持可控且不伪装已有统计真值。

## Implementation Decisions

### 1. 一个内部引擎，三个公开领域工具

内部建立共享 `DualSourceRecommendationEngine`，负责输入快照、通道编排、完整召回、
归一化、diff、固定组装、降级、幂等和审计。公开边界按领域拆成：

- `recommend-style-directions`
- `recommend-hairstyles`
- `recommend-wardrobe`

固定 workflow 与对话 Agent 只能调用上述领域工具。A/B 通道、diff 和 reviewer 都是内部
能力，不注册成 Agent 可自由组合的工具，避免 Agent 绕过确定性策略。

### 2. 产品流程严格分阶段

旧的「风格 + 发型原子选择」迁移为三个等待用户确认的阶段。用户明确选择的风格必须出现在
后续推荐上下文和最终结果中；系统可以给出其他推荐，但不能用系统更偏好的风格替换用户选择。
改变风格或发型会使其下游计算键失效并产生新一代结果，上游历史保持不变。

### 3. A/B 只改变系统知识，不改变用户输入

A/B 使用相同 provider、模型、模型版本、temperature、token 限制、工具 schema 和基础
prompt。供应商支持 seed 时使用相同 seed；不支持时记录 `stochasticComparison=true`。

A 不接收目录、规则、目录规模或召回摘要，避免系统知识泄漏。B 获得相同用户输入加系统
上下文。任何额外用户字段、照片或分析只能同时添加到两个通道。

### 4. 多模态输入按领域最小化

- 风格：正面照；有全身照时同时输入全身照。
- 发型：正面照；将来若已采集侧面照可增加侧面照，不需要全身照。
- 穿搭：正面照；有全身照时同时输入全身照。

输入只允许原始用户资产及其已存分析引用，禁止把发型预览、穿搭预览或其他生成图片送回
推荐模型。照片使用现有短时授权与访问日志；审计只保存资产引用，不保存签名 URL。

无全身照时穿搭仍运行，使用身高、体重、体脂、围度、锻炼情况和用户自报体型。输出标记
视觉证据缺失，理由不得声称观察到了身材比例，也不开放本人换装预览。

### 5. B 通道召回全部适用数据

召回不设业务 Top-K。先按当前领域、用户已选上游结果、场景、季节和数据自身适用条件找到
全部适用候选，再投影成紧凑结构；调研文章全文、评论原文和无关字段不进入模型上下文。

若紧凑结构仍超过模型上下文，按稳定 ID 进行确定性完整分批，各批可并行，最后用版本化
确定性策略合并。不得静默截断。审计记录 `retrievedCount`、`submittedCount`、
`batchCount`、输入字节数与估算/实测 token 数。

### 6. 两通道输出同一严格领域 schema

A 可创建目录外概念，但仍必须满足领域 schema；B 只能选择或组合召回集合中的稳定 ID。

- 风格：稳定/概念风格 ID、名称、定义、正式度、成熟度、张扬度、维护成本、场景、季节、
  体型适配与理由。
- 发型：稳定/概念发型 ID、长度、露额程度、发量要求、发际线与脸型适配、维护成本、
  风格关系与理由。
- 穿搭：公式 ID、风格 ID、槽位、品类、版型、廓形、颜色、材质、场景、季节、单品或
  概念单品引用与理由。

B 的每条规则引用包含 `ruleId`、`mechanism`、`evidenceLevel`（S1/S2/S3）、
`applicabilityConditions` 和实际 `applicabilityResult`。目录存在不等于规则正确适用。

### 7. diff 和组装完全确定性

不使用 LLM 辩论，也不使用同步 LLM 裁决。每个领域有独立的版本化 canonicalizer、
diff policy 和 threshold：

- 风格比较 canonical style、排名及四个风格向量方向；
- 发型比较 canonical hairstyle、长度、露额、发量要求、脸型适配理由和排名；
- 穿搭比较公式/槽位、品类、廓形、颜色、材质、场景、季节和排名。

共享 diff 输出包含 `diffScore`、`severity`、`dimensions`、`hardConflict` 和
`diffPolicyVersion`。固定组装顺序为：

1. A/B 共识候选；
2. 规则适用性成立的 B-only 系统支持候选；
3. 最多一个无硬冲突、通过确定性安全策略的 A-only 探索候选。

不会只取严格交集，避免交集为空时没有结果。风格与发型各返回 3 个主推荐、最多 1 个探索；
穿搭返回 1 个主公式、2 个备选、最多 1 个探索。没有合格探索时不补占位。

### 8. 失败时系统结果保证可用性

各通道有独立超时，默认配置范围为 8–12 秒，精确值由环境配置并写入审计。

- A/B 都成功：按正常 diff 和组装。
- A 失败：返回 B 与系统确定性结果。
- B 失败：返回系统确定性结果，并最多保留一个通过硬冲突检查的 A 探索候选。
- A/B 都失败：返回系统确定性结果。
- 系统目录不可用：只返回明确标记为 AI 探索的 A 结果，不声称系统验证。

确定性系统结果是可用性底座，不是第三个参与辩论的 LLM 通道。

### 9. 结构化持久化是核心资产

新增 `RecommendationComparisonLog` 及逐通道运行/事件关联。至少保存：

- domain、user、plan、recommendation set 和 generation 引用；
- `profileSnapshotRef`、`photoAssetRefs`、`appearanceAnalysisRef`、
  `questionnaireSnapshotRef`、`recommendationContextRef`；
- 年龄、身高、体重、体脂、围度、脸型与置信度、发际线、发量、当前发型、胡须、眼镜、
  当前穿着、场景、季节、预算、正式度和已选上游候选的版本化来源；
- A/B 候选、结构化理由、provider/model/prompt/schema 版本及调用结果；
- 目录、规则、召回、归一化、diff、组装策略版本；
- 规则命中、机制、证据等级和适用结果；
- 实际曝光候选、来源、位置，后续选择和强结果事件；
- reviewer 状态与分类；
- 成本、延迟、重试、缓存复用和随机性标记。

服务普通日志只记录这些对象的 ID、耗时和错误码，不记录原始推荐文本、照片、签名 URL、
完整 prompt 或模型 transcript。

### 10. 曝光、选择与结果分层

`exposure` 记录真正返回给用户的候选和位置；`choice` 记录用户选定项；`outcome` 记录保存、
槽位替换、明确不喜欢、保存试穿和最终采用等强事件。查看、滚动和停留不作为偏好信号。

比较 A/B 被采纳率时必须以实际曝光为分母，并保留来源和位置，避免把没展示过的候选当作
未采纳。用户选择只标记为行为证据，不作为客观正确性的标签。

### 11. reviewer 只处理高差异且异步运行

低差异记录 `reviewStatus=not_required`。高差异在用户结果持久化后排入 reviewer，
状态为 `pending|completed|failed`。reviewer 不能修改候选或阻塞响应，只输出：

- `agree`
- `rule_gap`
- `rule_conflict`
- `rule_misapplied`
- `llm_hallucination`

以及结构化说明、相关 rule ID 和复审建议。每个 comparison log 只允许一个幂等 reviewer
结果，不保存自由辩论 transcript。

### 12. 目录外概念和资产缺口保持可追踪

A-only 探索项使用稳定 `conceptItemId`。已映射槽位引用正式 `wardrobeItemId` 与资产；
未映射槽位返回 `catalogStatus=not_mapped`、`assetStatus=missing`、
`generationStatus=queued`。用户可以把结构化文字概念选入方案，但资产准备前不能真人试穿。

建立 `CatalogGap` / `AssetGenerationQueue`，用户选择提升优先级。后续通过
`ConceptCatalogMapping` 把概念映射到正式目录 ID、资产和审核信息。映射只影响之后的解析，
不得重写历史推荐快照或把过去的 AI 探索伪装成当时已验证的目录项。

### 13. 幂等按阶段、领域和通道拆分

计算指纹包含用户输入快照版本、资产版本、已选上游候选、目录/规则/prompt/model/schema/
diff/merge 版本和 generation。A/B 通道分别持久化 computation key；重试只执行失败通道。

重复请求复用成功结果。只有用户显式刷新、关键档案变化、上游选择变化或版本变化才创建新
generation。reviewer 也以 comparison log 为幂等键。

### 14. 隐私删除与同意撤回

用户存在时保留完整版本化引用链，便于解释为什么产生该推荐。账户删除或人脸处理同意撤回
后，删除照片、面部分析、可识别档案快照和对照记录中的用户关联；只允许保留无法重新识别
个人的聚合计数。不得仅把 user ID 置空后保留完整身体与面部特征组合。

### 15. 与现有 RecommendationApplication 兼容

共享引擎位于现有应用层边界内部，继续复用候选归属、付费调用前抢占、短时照片授权、
provider 输出校验、安全渲染指令、选择和生成资产生命周期。三个领域 adapter 输出仍归一化
为现有候选视图；对照日志不会通过用户推荐 API 暴露。

### 16. 迁移和发布

1. 先加入数据模型、共享契约、fake channel 测试和关闭状态下的引擎。
2. 接入风格领域并把旧原子选择拆成风格选择点。
3. 接入发型领域，要求已选风格作为输入。
4. 接入穿搭领域，要求已选风格和发型，复用系统衣柜。
5. 以内部 feature flag 小流量启用并核对调用成本、失败降级和删除链路。
6. 确认三个阶段均可恢复和回放后再设为默认。

已有 `RecommendationCandidate` 不回填为 A/B 记录，不改写来源。旧未完成方案在用户继续时
按新的最近有效选择点重新生成下游结果。

## Testing Decisions

最高且主要的测试接缝是三个公开领域工具经过 `DualSourceRecommendationEngine` 的完整返回
和持久化副作用。测试注入 fake A/B channel、fake recall、fake reviewer 和真实测试数据库，
不依赖具体模型供应商，也不直接断言私有 helper 或 prompt 文本。

三个领域 adapter 共用一套契约测试，并补充领域 diff fixture。该接缝必须覆盖：

- A/B 收到相同用户与原始资产输入，只有 B 收到系统上下文；
- A/B 并行执行，相同 provider/model/参数被记录；
- 完整召回、超限分批、确定性合并且无静默截断；
- 共识/B-only/A-only 的固定顺序、数量上限和硬冲突处置；
- 用户已选风格在发型与穿搭上下文中不可丢失；
- 单通道失败、双通道失败、系统目录失败及无全身照降级；
- 通道级 computation key、缓存复用、独立重试和 generation 失效；
- 对照、曝光、选择、强结果事件和实际 exposed source/position 落库；
- reviewer 只在高差异异步触发，且不进入用户响应；
- 概念条目、CatalogGap、资产队列、后续 mapping 与历史不可变；
- 账户删除/同意撤回清除可识别引用，只保留匿名聚合；
- 任何推荐通道都不接收生成图片。

在此之上只保留少量 workflow 集成测试，验证三个等待用户选择的阶段、422 前置条件和下游
失效。模型 adapter 另有 schema/供应商冒烟测试，但不作为业务验收主接缝。

现有推荐应用层、天气感知 runner、风格选择路由和 workflow step 测试作为测试组织方式的
先例；新测试应复用其依赖注入、真实数据库 round-trip 和幂等断言风格。

## Out of Scope

- 当前版本不训练 embedding、排序模型或个性化向量数据库。
- 当前版本不根据相似年龄/身高/体型人群自动改写排序；仅收集未来需要的版本化数据。
- 当前版本不把用户选择当作审美真值，也不自动提升/降级规则证据等级。
- 当前版本不做 LLM 辩论、同步裁决或多轮自我反思。
- 当前版本不自动抓取淘宝、小红书、抖音商品或博主数据。
- 当前版本不解决商品实时价格、库存、购买链接和联盟归因。
- 当前版本不保证每个探索概念立即有商品图或本人试穿图。
- 当前版本不对浏览、滚动、停留等弱行为做偏好学习。
- 当前版本不向用户展示 A/B 技术标签、diff、内部规则 ID 或 reviewer 结论。
- 当前版本不迁移或重写历史自由文本候选。

## Further Notes

未来群组倾向可按年龄段、5cm 身高段、BMI/体型、场景、季节和风格上下文分桶；建议至少
30 个实际曝光用户才启用低权重，30–100 保持低权重，超过 100 再使用正常权重。无论群组
样本量多大，用户本人明确偏好和选择都应高于群组先验。该算法不属于本变更。

“全部召回”指全部适用候选，而不是把整个数据库和调研原文无差别送进模型。完整性由
`retrievedCount == submittedCount` 或完整分批证明；紧凑投影、稳定分批和确定性合并是
上下文安全的一部分，不是候选数量限制。
