# Design: 可替换的方案推荐能力

依据强度：`实测` 有实验数据 / `逻辑推演` 从既有约束推出 / `产品决策` 用户拍定。

规范文本见 `../../../docs/specs/pluggable-style-recommendation.md`。

## 1. 本地数据不是前置条件

`产品决策`

目录为空、风格向量缺失、双审美调研不存在，都不阻断流程。
多模态 Agent 暂时充当推荐知识的实现，输出带来源与验证等级标注。

代价是明确的：这一阶段的推荐依据不可复现、不可审计。
换取的是整条链路（采集 → 推荐 → 出图 → 选择 → 方案落地）现在就能跑通并验证。

## 2. 唯一对外入口是应用模块，不是 provider

`逻辑推演`

只让固定管道与对话 tool "共享同一个 provider" 不足以防止行为分叉：
两个入口仍可各自实现抢占、幂等、照片授权、输出校验、候选落库。

因此这些职责收进 `RecommendationApplication`，provider 降为内部可替换 adapter。

首版接口只有 `recommendHairstyles` / `recommendOutfits` / `selectCandidate` 三个方法。
换一批、多代级联失效、对话入口以后在同一接口上增加，不改变这三个方法的语义。

## 3. 抢占必须先于付费调用

`逻辑推演`

若顺序是"调 provider → 校验 → 落库"，两个并发请求会同时查不到就绪集合、
同时调用付费 provider，最后才在唯一键上竞争：数据库只留一个集合，费用发生两次。

因此先原子 insert-or-get `RecommendationSet(status=preparing)`，
只有创建者调用 provider，其余请求读取该集合。

`computationKey` 组成含 `generation`（首版恒为 1）。
现在就纳入，避免将来加换一批时键定义变更导致已有数据失效。

## 4. provider 不返回最终图生图指令

`逻辑推演`

provider 返回受限的 `visualDirection`（造型描述），应用模块校验后放入固定模板，
统一追加身份保持与禁止修改项。

若 provider 直接产出送往图生图的完整指令，可替换 adapter 就获得了改动身份、背景、
体型的通道，也可能与身份保持后缀冲突。

模板在应用模块而非目录上：目录首版可以为空，模板不能因此缺失。

## 5. 用户数据全程可用；只有造型属性估计这一次调用被限制输入

`实测`

**客户端采集与计算出的数据是权威输入，推荐调用完整接收**——
脸型分类与支撑比值、发际线状态（后移判定实测 0/17 假阳性）、
发量状态、身体数据、问卷各项。缺的是审美知识，不是用户数据。

被限制的只有"造型客观属性估计"这一次调用：它答的是**造型自身的属性**
（背头是否露额，与穿它的人无关），因此不接收用户的发量与发际线信号。

依据是一次实测：模型得知"用户发际线偏后、约束要求遮额"之后，
把客观上露额的侧分背头与平顶都标为遮额；正常发际线场景下同类造型标为露额。
同一类造型在两个场景标注相反，翻转方向朝着"能通过约束"。

因此 `agent_estimated` 不是"未验证"，而是**已知乐观偏置**——
除非把估计调用与用户数据隔离。

真正用用户信号做判断的是代码侧的可行性过滤，它是确定性的，不会迎合。

**这条限制只在目录为空的阶段存在**，目录到位后属性从目录读，估计调用消失。

## 6. 能力状态显式返回，措辞与状态绑定

`产品决策`

每个候选集返回 `capabilityStatus`，四个维度各有取值：
知识来源、可行性验证、穿搭协调验证、预览质量检查。

`agent_estimated` 只能表述为主观判断或估计，
`catalog_verified` 只能表述为通过当前目录属性规则检查，
`not_checked` 必须显式告知未自动校验。

不输出没有定义测量对象的 `confidence`、匹配度百分比或双审美数字。

## 7. 生成图片先落库再签发读取地址

`实测`

当前预览图经 `persistGeneratedImage` 写入 OSS，**不写任何数据库行**；
`storageKey` 只存在于 job 的 `partialResult` JSON 里。
而删除链路的 `all_generated_images` 与 `account` 只枚举 `TargetImage` 表。

后果是删除全部生成图或删号时，预览图的 OSS 对象不会被删掉。

因此所有生成图片先建 `GeneratedAsset` 再对用户签发读取 URL，
删除链路统一从该表枚举 OSS 对象。

## 8. 付费调用状态只有三个终态

`实测`

存在无法消除的崩溃窗口：写 `prepared` → HTTP 已被供应商接受 → 记录结果之前崩溃。

火山引擎的 `CVSync2AsyncSubmitTask` 不接受客户端幂等键，
也没有按客户端键列出任务的接口；`resumeVolcVisualTask(callId)` 需要的 task_id
正是崩溃窗口里丢失的东西。

因此状态为 `prepared → succeeded | failed | unknown`。
过期的 `prepared` 一律转 `unknown`，不自动重提，全部进人工对账。
不引入 `submitted`：它只把窗口从"记录前"缩到"读响应前"，关不掉，
承认不可知比假装可分辨更诚实。

## 9. 输入按域拆分

`逻辑推演`

共用输入超集会导致：纯文字穿搭被迫获得人脸照片 URL；
天气变化让发型指纹变化并触发无谓的重新付费；
发量信号暴露给穿搭 adapter、围度暴露给发型 adapter。

因此两个域各自定义输入，指纹分域计算。
穿搭的 `fullBodyPhotoReadUrl` 为可选，纯文字路径不传。

## 10. 不能用 LLM 兜底的能力

`逻辑推演`

同意与成年门槛、归属校验、幂等与抢占、费用状态、用户实际选择、访问授权日志、
删除链路、内容标识、限流与字段级安全，必须由确定性代码与持久化状态保证。

Agent 的文本不能作为这些能力已完成的证据。

## 11. 三阶段替换路径

`逻辑推演`

```
阶段 A  multimodal-agent   直接产出候选，catalogVariantId 为空，agent_estimated
阶段 B  hybrid             目录提供候选与客观属性，LLM 负责排序与解释，catalog_verified
阶段 C  catalog-matching   本地规则完成过滤与排序，LLM 只负责解释或退出
```

三阶段输出同一个 `RecommendationSetView`，共用同一套 Candidate、GeneratedAsset、
`selectCandidate`、S4 与 S5 链路。
