# Spec：发型环节内的假发可选项

本文取代 `wig-assisted-hairstyle-options.md`。术语以根仓库 `CONTEXT.md` 为准。

关联 ADR：`docs/adr/0002-keep-style-rules-separate-from-brand-and-sku-supply.md`
（只产出「需要哪种形态的假发」，不引入假发供给/SKU 数据）。

**范围硬约束（产品决策）：改动只落在发型推荐这一环。** 不触碰风格方向选定、穿搭、
出图链路、首轮分析，也不改任何跨环节的集合失效语义。这条约束不是谨慎，而是本能力的
定义边界 —— 它要解决的问题完整地位于发型这一步之内。

---

## Problem Statement

用户在引导流自报「受脱发 / 发量变少的困扰」，其中最重一档是「明显困扰，想重点改善」。
选定风格方向后进入发型推荐时，系统会按 `Hair Volume Signal` 推导出的约束，把需要更多
量感、或会把发际线暴露出来的款式**静默剔除**。

于是这批用户在发型这一步看到的选项比别人少，而且：

- 他们不知道被剔掉的款式存在；
- 更不知道存在另一条能达成它们的路径；
- 对一个「下周就要见重要的人」的用户，「养几个月发量再说」等于没有答案。

系统收下了他们最强的改善意愿，却在这一步只给了更短的列表。

## Solution

**在同一步里多给一组选项**，不改这一步的任何其他行为。

被剔除的那批款式并不是无从判断的黑箱：发型可行集来自确定性的目录投影，投影时被发量/
发际线约束剔掉的部分是**规则算出来的完整补集**，而且每一项都带明确原因。这批款式恰好
就是「只差发量或发际线」的款式 —— 也就是假发能解决的那一类。

于是流程只多一段，全部在发型这一步内：

1. 目录投影照常给出用户**当下就能剪**的可行集（这一段完全不变）。
2. 被发量/发际线约束剔掉的那批，交给一次**确定性查表**，判断每款需要哪种形态的假发
   （只补量感 / 整头更换），以及是否根本做不自然（例如极短露头皮款式）。
3. 满足开放条件时，发型这一步出现一个**独立入口**；点进去是一批呈现方式与普通发型
   完全一致的款式，每项带明确的达成路径标签。

核心概念仍是 `CONTEXT.md` 里那对区分：`Hair Volume Signal` 是对用户**自身**头发的观察，
`Available Volume Premise` 是他造型时**实际可动用**的发量。**假发改变前提，不绕过约束。**

## User Stories

1. 作为自报「明显困扰，想重点改善」的用户，我希望这个回答真的让发型这一步给我更多选项，而不是被系统收下后丢掉。
2. 作为下周就要见重要的人的用户，我希望在选发型时就知道短期内能做到什么，而不是只拿到一个需要几个月的方向。
3. 作为自身发量撑不起某些款式的用户，我希望知道这些款式存在，以及它们需要什么条件才能达成。
4. 作为只想补一点量感的用户，我希望系统告诉我发片就够，不要让我以为必须买整顶假发。
5. 作为想尝试露额造型的用户，我希望知道这类款式对假发的前额工艺要求更高。
6. 作为发量正常的用户，我希望发型这一步完全不出现假发相关内容，包括任何暗示我可能需要它的措辞。
7. 作为短发用户，我希望不因为「照片上头发短」被误判成发量少，从而被推荐假发。
8. 作为发际线天生偏高、但从未表达过任何困扰的用户，我希望系统不要替我决定我该买假发。
9. 作为「就是日常」场景的通勤用户，我希望假发流程完全不出现 —— 它不解决我的问题。
10. 作为用户，我希望假发款是我主动点进去看的，不要混在主候选列表里让我被动接受。
11. 作为用户，我希望入口上写的「能解锁 N 款」是真实数字，点进去不要发现是空的或只有一款。
12. 作为用户，我希望一个只有戴假发才能达成的效果图明确标注达成路径，不要让我以为剪个头发就能变成那样。
13. 作为用户，我希望这个达成路径标签一路跟到我的方案与变更清单里，不只出现在选择的那一瞬间。
14. 作为用户，我希望假发款的效果图看起来就是我戴上之后的样子，不要出现网底、发根断层这类一眼假的痕迹。
15. 作为用户，我希望系统在这件事上从不使用诊断性表述 —— 不说我脱发，只说款式需要什么条件。
16. 作为用户，我希望系统在判据不足时宁可不推荐，也不要让我花钱买一顶做不出目标效果的假发。
17. 作为不使用假发的用户，我希望发型这一步给我的主列表和今天完全一样，不因为多了这个功能而变化。
18. 作为用户，我希望假发款不跨越我已经选定的风格方向。
19. 作为数据维护者，我希望「某款式在假发前提下是否可行」这一维有明确的依据强度标注，能区分实测与逻辑推演。
20. 作为数据维护者，我希望这一维在没有依据时能安全留空 —— 留空即不推荐，而不是留空即放行。
21. 作为数据维护者，我希望这一维的每条结论都能追溯到 `Evidence Source`，且范围明确排除 cosplay / 彩色 / 舞台 / 女式假发。
22. 作为工程师，我希望这次改动不新增任何模型调用。
23. 作为工程师，我希望假发判定逻辑集中在既有的纯函数里，不需要数据库或模型替身就能测。
24. 作为工程师，我希望不新增接缝 —— 复用发型链路上已经存在且已有测试的那两个。
25. 作为工程师，我希望假发数据未回填时，发型这一步的行为与今天逐位一致，不产生回归。
26. 作为工程师，我希望这次改动不碰风格方向选定、穿搭、出图与首轮分析。
27. 作为合规负责人，我希望入口的触发依据可审计地表述为造型可行性，任何环节都不出现健康或诊断口径。

## Implementation Decisions

### 差集就是目录投影的排除集（推翻「两轮推荐」）

**前一版 spec 的核心机制是跑两轮推荐、取差集。本文推翻它。** 理由必须写清，否则会被当成
偷懒回退：

前一版建立在「候选由模型产出、确定性规则事后过滤」这个前提上。在那种前提下，被排除的
候选是**一次模型输出的残余** —— 数量取决于模型这次挑了什么、没有排序依据，而且与
「不足就是不足、不回填被排除项」的既有原则冲突。所以当时选了两轮：让模型在两个前提下
各自认真推一遍，两个列表各自完整。

但发型推荐这一步的可行集**不是**那样来的：它来自确定性的目录投影 —— 先按风格关系取出
合规的发型池，再用同一份可行性约束过滤。被剔掉的部分是**规则算出来的完整补集**，与模型
挑了什么无关，也不存在采样波动。于是：

- 不需要第二轮：补集已经在手，且是完整的。
- 不需要第二次模型调用：整段推导是纯计算。
- 不需要「差集要重新核验是否真被自身发量挡住」：补集里每一项**定义上**就是被挡住的。
- 与「不回填」原则不冲突：那条原则防的是拿模型做不出来的东西凑数，而这里补集带着明确
  的排除原因，且被单独呈现、带达成路径标签，不混进主列表充数。

顺带解决一个次生问题：风格方向选定会让该方案下所有发型集合失效。前一版把推导放在首轮
分析里，因此会被这个语义打穿；本文的推导发生在风格选定**之后**的发型推荐步骤内，不涉及
跨阶段集合，问题自然消失 —— 这也正是「只影响发型这一环」这条约束带来的好处。

### 排除集要带出可行性属性

发型目录投影目前的排除集只有款式 id 与原因文本，丢掉了款式名与它**内部已经算出来的**
两个可行性属性（发量需求档位、是否遮额）。假发形态匹配需要这两项，所以投影要把它们
一并带出。**纯追加**：现有消费方读不到新字段也不受影响。

不从别处重新查这两个属性 —— 那会产生第二个真相来源，而投影里那份才是过滤实际使用的。

### 假发方案推导（复用既有纯函数，改其入参）

既有的假发方案推导纯函数保留全部职责：开放条件判定、形态匹配、fail closed、模板文案。
**入参从「两轮候选 + 发量信号」改为「被挡住的那批候选」。**

两轮那个形状是为已被删除的模型路径设计的，保留它等于为一个不存在的调用方留抽象。

开放条件仍是三条**同时**成立：

- **场景门槛**：方案为短期赛道。理由不只是复用既有字段 —— 假发的主张是「**短期内**剪发
  达不到」，而只有短期这一支收集了目标日期，其余场景无从主张「来不及」。
- **用户侧依据**：问卷自报脱发/发量困扰为非「没有困扰」，或用户在选择界面显式确认。
  这条是硬门槛：**视觉信号可以影响「推荐哪些发型」，但不能替用户决定他该买东西。**
- **真实可解锁**：形态匹配后可行款 ≥ 1。为 0 时不显示入口，因为入口上的数字必须真实。

### 形态分档

形态由数据推导得出，不是产品拍定 —— 排除集按「被什么挡住」天然分成三类：

| 排除原因 | 形态结论 |
|---|---|
| 仅发量不足（款式本身遮额） | 只补量感（发片）即可，不必整顶 |
| 遮额约束（露额、非极短） | 需整顶，自然度取决于前额工艺 |
| 遮额约束（极短露头皮） | **排除** —— 整顶假发做极短款不自然 |

第三类是必需的排除项而非多余谨慎：极短款式（寸头类、渐变类）发量需求本来就低，它们进
排除集是被**遮额**约束挡住的；一旦假发解除该约束，它们会被判成「可行」，而整顶假发做
一公分寸头是最容易露馅的场景。

所需档位取「被什么挡住」与属性表标注**更严的一方**：标注讲款式本身的工艺门槛，前者讲
用户为什么做不到，两者都成立才是真的可行。

### 数据：发型属性表的假发维度（已就位，待回填）

维度结构与 fail closed 语义已实现：**未标注 = 未判定 = 不可行**。标错的代价是让用户花钱
买一顶做不出目标效果的假发，比少推荐一款严重得多。

- 依据强度**在有实拍对照之前不得标注为「实测」**，上限是逻辑推演。类型层面已挡住。
- 判据不足的款式保持留空，其标注缺口按数据维护任务处理 —— 缺口是属性表的属性，不是
  某个用户的属性，因此不依赖运行期是否有人命中。

### 呈现、文案与出图

- 假发款**不混入主候选列表**，放在独立入口之后；入口之内呈现方式与普通发型一致。
- 达成路径标签随方案持久化，在方案落地时写进变更清单条目的变化描述与理由（**已实现**）。
- **出图链路不改。** 现状已是「先返回文本候选、用户选定后才出图」，假发款走同一条路。
- 图生图指令中**不出现「假发」字样**：发型渲染文案按图像供应商逐款校准，引入未校准语义
  需整套重测，而图该画的本就是「戴上之后长什么样」。达成路径是元信息，不是图像内容。
- 面向用户的假发文案用**模板**，不交由模型措辞 —— 该表述紧邻「不做医学诊断」红线，
  而已有实测表明模型在明确禁止后仍会产出诊断性表述。

### 不改动的东西（范围约束的具体化）

风格方向选定与集合失效语义、穿搭推荐、首轮分析、出图链路、发型主候选列表的产生方式。
穿搭没有发量前提，不得为它引入该概念。

## Testing Decisions

好的测试只断言外部行为：给定被挡住的款式与门槛输入，输出的假发方案是什么。不断言中间
数据结构、不断言调用次数、不为覆盖率去测私有分支。

**不新增接缝。** 复用发型链路上已存在、且都已有测试的两个纯函数。

### 接缝一：发型目录投影（已有测试）

- 排除集带出款式名与两个可行性属性，且值与过滤实际使用的一致。
- 现有消费方行为不变（纯追加）。
- 主可行集与今天逐位一致。

### 接缝二：假发方案推导（已有 15 条测试，随入参调整）

- 被挡住的集合为空 → 不产生方案。
- 非短期赛道 → 不开放，即使有被挡住的款式。
- 缺用户侧依据 → 不开放，即使赛道与集合都满足。
- 仅发量不足且本身遮额 → 只补量感形态。
- 遮额挡住的非极短款 → 整顶形态。
- 极短露头皮款 → 排除，不出现在方案中。
- 属性表未标注 → 不进入方案（fail closed），并产出标注缺口信号。
- 可行款为 0 → 不开放入口。
- 所需档位取两个来源中更严的一方。
- 面向用户的标签来自模板，且不含健康/诊断字样。

### 不设为接缝

发型推荐步骤的接线。逻辑全在上面两个纯函数里，而为它搭替身需要任务、持久化与供应商
全套，成本高而逻辑薄。

### 先例

发型目录投影与发型属性表都已有测试文件；确定性规则测试与变更清单任务构造测试同理。
运行方式：`npm test`（先构建，再以 `node --test` 跑编译产物）。

## Out of Scope

- **假发供给与采购**：品牌、价位、SKU、商品图授权。本轮只回答「你需要什么规格的假发」，
  不回答「买哪一顶」。前置条件不满足：内容安全审核 provider 未选定，商品图的可审计授权
  基础比服装 SKU 更难建立。
- **把工艺维度标注为「实测」**：需要真实购买样本做实拍对照。
- **织发 / 补发等须到店的半永久服务**：调研会覆盖，本轮不进入推荐产物。
- **假发任务落入哪个改善阶段**：取决于调研中「可自行购买」与「须到店」的区分。
- **场景门槛扩展到「正式聚会」等场景**：需先为这些场景补收目标日期，否则无法主张
  「短期内来不及」。
- **服务端接收「显式确认」的入口**：开放条件已支持，但现在加字段与端点没有任何调用方，
  与客户端一并实现。
- **客户端**：入口、开关、标签呈现、状态流转。
- **假发预算**：不占用穿搭预算档位，也不新增预算问题。

## Further Notes

**这个能力对「视觉发量判定不可靠」是免疫的**，值得单独记下：仅视觉判定发量偏少时既有
规则返回无约束（实测依据：正面照分不清「头发短」与「发量少」，据此过滤会误伤大量短发
用户），因此视觉发量误判**单独不会**产生任何假发候选；再加上用户侧依据这道硬门槛，
无论测得准不准都不会有人被误推假发。换言之，本能力不依赖任何本仓库已知不可靠的信号。

**一处可能变成多余的表面**：前一版为「两轮推荐」在发型推荐应用层加了可用发量前提入参
并把它计入输入指纹。本文不再需要那次额外调用，实现时应判断它是否已无调用方 —— 若是就
一并删掉，别留着。（约束推导函数上的前提入参不同：它承载 `Available Volume Premise` 这个
领域概念，且已有测试覆盖，保留。）

**合规口径**：入口的触发依据在任何环节都表述为造型可行性（「在你的发量条件下可行款式
不足」），而非健康或诊断结论。用户发量足够时这段推导不产生任何输出，他不会看到这个概念。
